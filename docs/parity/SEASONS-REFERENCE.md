主整合採用的日曆方向：航程第 1 天對應「航程 1 年 6 月 1 日」，依 Gregorian 月長／閏年推進，day 限制 1–9999；春 3–5 月、夏 6–8 月、秋 9–11 月、冬 12–2 月。**這整套紀年與分季為本作原創，不是已證實的 Wii 初始日期或季節表。** 航程年不是電腦當年，關閉網頁後不偷偷按真實時鐘推進。若使用 JavaScript Date，注意 `Date.UTC(1, …)` 會被當作 1901 年，宜用整數日算法或明確設定完整 UTC 年，且不可混入本機時區。

玩家流程應是一個閉環：船艙時鐘查看日期與來訪提示 → 等候至合適時段 → 移船並下水 → 親眼找到已出現的實際個體 → 有效觀察／真實取景拍攝 → 回船保存 → 下一季重訪時看見內容改變。玩家 UI 用「目前在此海域活動／預計下一季再訪」等文字即可；原作查證與精確科學界線留本文件及圖鑑資料，不塞進每個控制。

## 最小介面與狀態約定

以下是整合契約建議，名稱可隨主實作調整，無需為未來可能性建立通用排程框架。

- `calendar(day, minute)`：純函式衍生年／月／日／季節／時段；舊存檔 day 與 minute 原值直接延續，不重置航程。
- `schedule(speciesId, clock)`：只回傳計畫窗口及下一個可達窗口；未知物種預設常住，未知輸入不能拋出例外或無限搜尋。
- `available(f)`：依同一個實際 actor 的排程與暫留狀態作唯一判定；已擁有夥伴與水族館展示不因野外季節而消失。圖鑑仍保留已知內容，離場不是忘記或刪除個體。
- `advanceTime(request)`：船上受限入口，先驗證有限整數／支援動作，算出結果再一次提交、刷新視覺／排程／甲板與保存。day 到上限應明示不能再等，不可 wrap 回第 1 天、接受負值或存入 NaN。
- 野外排程離場不能復用 `faunaVisibility`：後者已有鑽洞／警戒與 0.8 觀察門檻。避免改 `life` 的順序、UID、home 或在每季重建 GPU geometry；動態 flags／既有 instance 可見性即可。
- 時段在潛水中跨界時，眼前、正跟隨／微觀觀察／抓握的動物先暫留，離開觀察範圍後再離場。暫留應有實際可見判定與視距上限，不能玩家看向遠方就永久擋住離場；一旦離場須清除對它的 focus／follow／micro 等引用，避免隱形拍攝或鏡頭鎖死。開拍、等待與入場的變化也須避免眼前突然生成。
- 計畫窗口與实际暫留分開：圖鑑提示「活動時段已過，目前仍在附近」不能誤寫為「已離開」；下次新潛次、匯入、重設時重新計算，不能沿用舊世界的 cache。
- 採集／照片與進度仍用既有真實保存身份。照片的 `date` 是唯一附件身份，不得換成遊戲 day/minute；若需記錄拍攝季節，另加可選 metadata，既有圖像、照片 pin、郵件與 photoCredits 不變。
- 跨季不應增加 ecology encounter 次數、清空 field／individuals、撤銷水族館資格或退役夥伴。新一季不是假發現事件；仍需真實距離、視線、可見度及觀察時間。
