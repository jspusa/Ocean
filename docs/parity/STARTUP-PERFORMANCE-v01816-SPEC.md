# 0.18.16 入海效能與房間恢復

固定基準 `07ac078ca0e2a72e70d005888836725aec1a9882`，承接 0.18.15 已發布後仍重現的初入海慢幀與多人 Stage A 重連缺口。完整商用及 Wii 功能範圍仍由總規格／工作單追蹤。

## 玩家行為與畫面

1. 保留預設桌機／觸控自動畫質、原始解析度預算、MSAA 支援選擇、60／30 場景提交與 120 Hz 物理；不以預先降畫質或更改量測數字掩蓋負載。
2. 同一 Renderer／WebGL context 的格式取樣支援只查詢一次；切換尺寸、品質或自動解析度使用該 context 的結果。不同 context 不共用能力，浮點與一般色彩格式分開，空支援結果也須正確保存。配置候選仍完整檢查，失敗保留舊畫面並釋放候選。
3. 水面光學與波浪運算只接受經正式 shader、相同場景／時間／解析度／MSAA 的全 RGBA 驗證及 GPU 成本支持的等價優化；保留全反射、斯涅爾窗、天空透射、不同光照與水面上下視角。實驗未證明的候選不得當作已改善。
4. 新增有界的 kind=0／material=12 船體 fragment 特化，保留原始頂點程式、全部運算與繪製順序；包含甲板／船艙物件及記錄器。失敗時回退原通用程式，不在每幀重編譯。固定解析度下須完整逐像素驗證，且正常自動畫質入水驗證不能預先降低解析度。
5. 自動畫質切換、視窗尺寸、方向與冷區塊等待繼續保留上一張畫面；不增加中心自動魚名或改動選取、自由探索與保存。

## 證據與實作順序

沿既有正式渲染／配置介面及正常 UI 的驗證邊界，先記錄基準再逐個切片 RED→GREEN。能力查詢使用正式配置函式及 WebGL IO 記錄；不以重抄新 helper 公式作測試。原生診斷維持正常入口、原速度與預設自動畫質；逐幀計錄完整 render、resize、stream、updateLife 與 GPU 整幀時間。冷／暖入海都記錄解析度差異，不當成固定工作量 A/B。GPU 計時與取樣本身可能干擾結果，不換算普遍 FPS 或功耗。

初步原生基準已證明 resize 約 62–85 ms，其中格式能力查詢約 19–28 ms，framebuffer 驗證約 40–55 ms；一般 CPU render 約 0.6–1.4 ms。保留必要配置檢查，不因有同步成本就刪除安全條件。第一版分 pass timer 在 Metal 回傳互相重疊的數值，不能相加或用來歸因，已改用整幀 query。

能力快取的後續實測：重複查詢降為零，但等待轉移至後續 framebuffer 驗證；四次 resize 仍約 62–82 ms，不能宣稱整體尖峰改善。全反射分支提前返回的第一輪固定視角實驗沒有穩定 GPU 收益，因此尚未採用。下一個實驗只將 fragment 的十個波浪迭代顯式展開，保留原公式、累加順序與頂點位移；同樣須完整像素與原生 GPU 證據。

官方依據：[WebGL 2 格式能力查詢](https://developer.mozilla.org/en-US/docs/Web/API/WebGL2RenderingContext/getInternalformatParameter)、[WebGL 避免阻塞呼叫](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices#avoid_blocking_api_calls_in_production)。本機數據為實際測量，文件只支持 API 語義。

## 多人恢復

## 船體像素驗收決策

第一輪正式實作測試在甲板發現 101／16,384,000 個 RGBA 通道差異，最大 1／255；初始水下與仰看船底完全一致。原嚴格結果保留為 `v01816-vessel-native-exact-failure.json`／`.log`，不改標成功。使用者要求保留可見畫質；經獨立覆核，採用水面實驗已有的有限數值容差，並增加重複性與 alpha 保護。這是工程驗收決策，不宣稱差異原因已證明為編譯器捨入。

後續所有視角／兩種 profile、時間 8 與 45 秒，在相同解析度／MSAA／繪製內容下：RGB 每通道差異至多 1／255，變更 RGBA 通道嚴格少於 0.01%，alpha 完全相同；兩次 generic 區塊須與基準 SHA 完全相同，兩次 production 區塊彼此 SHA 完全相同。保留原 VS 與實際附掛 shader、GL、context 及工作量檢查。容差開關必須明示，預設仍為嚴格模式；報告分開列出完全一致及容差內的視角，不能統稱逐像素相同。若任何一項超出，回到實作診斷，不繼續放寬。
